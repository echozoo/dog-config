# 业务通用配置管理系统需求规格说明书

**版本：** v1.0
**文档状态：** Draft
**系统名称：** Business Config / 业务通用配置管理系统

---

## 1. 项目背景

在业务系统开发过程中，经常会存在大量零散的业务配置和基础设置。

例如：

* 订单自动取消时间
* 是否允许超卖
* 单次最大购买数量
* 默认物流商
* 库存预警值
* 是否开启某项业务能力
* 会员注册赠送积分
* 某个业务策略参数

这些配置通常只有少量字段。

如果每个业务模块都为这些配置单独创建数据表，会产生大量结构简单、数据量很小的配置表，增加数据库设计、开发、维护和变更成本。

因此，需要建设一个统一的**业务通用配置管理系统**，用于集中管理这些零散的业务配置项。

---

# 2. 项目目标

系统的核心目标是：

> 为业务系统提供统一的基础配置管理能力，将零散、低频、少量的业务配置统一存储、统一管理、统一访问，避免业务模块因为少量配置数据重复创建独立配置表。

系统重点解决以下问题：

1. 业务配置统一管理。
2. 减少业务模块中的配置表数量。
3. 提供统一的配置数据模型。
4. 提供统一的配置查询 API。
5. 支持不同的数据类型。
6. 支持配置默认值。
7. 支持配置项描述和管理。
8. 支持通过 Page → Group → Item 对配置进行组织。
9. 支持管理后台以合适的组件展示配置。
10. 为后续扩展租户、作用域、权限、配置历史等能力预留空间。

---

# 3. 系统定位

本系统不是 Nacos、Apollo 这类应用运行时配置中心。

系统主要解决的是：

> **业务通用配置管理问题。**

### 不属于当前版本的核心能力

以下能力暂不作为 V1 核心需求：

* 服务注册与发现
* 应用配置推送
* 长轮询
* 配置实时监听
* 集群一致性
* Raft
* MQ 配置通知
* Redis 分布式配置缓存
* 应用启动配置管理

这些能力如果未来有需要，可以作为独立能力进行扩展。

---

# 4. 核心概念

系统采用三级配置模型：

```text
Page
  │
  ├── Group
  │     ├── Item
  │     ├── Item
  │     └── Item
  │
  ├── Group
  │     ├── Item
  │     └── Item
  │
  └── Group
        └── Item
```

即：

> **Page → Group → Item**

---

# 5. Page

## 5.1 定义

Page 表示一个业务配置域或配置场景。

Page 不单纯表示前端页面，而是一个业务配置的一级组织维度。

例如：

```text
订单配置
商品配置
库存配置
物流配置
会员配置
```

推荐代码模型：

```text
ConfigPage
```

---

## 5.2 Page 示例

```text
订单配置
├── 基础设置
├── 自动取消
├── 库存设置
└── 售后设置
```

其中：

```text
订单配置
```

就是 Page。

---

## 5.3 Page 属性

Page 至少包含：

| 字段          | 说明   |
| ----------- | ---- |
| id          | 主键   |
| code        | 唯一编码 |
| name        | 配置名称 |
| description | 配置描述 |
| status      | 状态   |
| sort        | 排序   |
| created_at  | 创建时间 |
| updated_at  | 更新时间 |

---

# 6. Group

## 6.1 定义

Group 是 Page 下的配置分组。

用于进一步组织配置项。

例如：

```text
订单配置
├── 基础设置
├── 自动取消
├── 库存设置
└── 售后设置
```

其中：

```text
基础设置
自动取消
库存设置
售后设置
```

就是 Group。

---

## 6.2 Group 属性

| 字段          | 说明      |
| ----------- | ------- |
| id          | 主键      |
| page_id     | 所属 Page |
| code        | 分组编码    |
| name        | 分组名称    |
| description | 分组描述    |
| status      | 状态      |
| sort        | 排序      |
| created_at  | 创建时间    |
| updated_at  | 更新时间    |

---

# 7. Item

## 7.1 定义

Item 是系统最核心的数据对象，表示一个具体的业务配置项。

例如：

```text
订单自动取消时间
是否允许超卖
最大购买数量
默认物流商
```

---

## 7.2 Item 示例

```text
订单配置
│
└── 自动取消
    │
    ├── 自动取消开关
    │
    └── 自动取消时间
```

配置项：

```text
key = order.auto.cancel.enabled
value = true
type = BOOLEAN
```

以及：

```text
key = order.auto.cancel.minutes
value = 30
type = INTEGER
```

---

# 8. Item 数据模型

Item 至少包含以下属性：

| 字段             | 说明       |
| -------------- | -------- |
| id             | 主键       |
| group_id       | 所属 Group |
| key            | 配置 Key   |
| name           | 配置名称     |
| value          | 当前配置值    |
| default_value  | 默认值      |
| value_type     | 数据类型     |
| component_type | 管理组件类型   |
| options        | 可选项      |
| description    | 配置说明     |
| required       | 是否必填     |
| status         | 状态       |
| sort           | 排序       |
| created_at     | 创建时间     |
| updated_at     | 更新时间     |

---

# 9. 配置 Key

配置 Key 是业务系统访问配置的核心标识。

例如：

```text
order.auto.cancel.enabled
order.auto.cancel.minutes
order.allow.over.sell
order.max.buy.quantity
```

配置 Key 应具备唯一性。

推荐：

> Item 的 Key 作为业务访问配置的稳定契约。

Page 和 Group 主要负责：

* 管理组织
* UI 展示
* 配置分类

而业务系统访问配置时主要依赖：

```text
key
```

这样即使未来调整 Page 或 Group 的组织结构，也不会影响业务代码。

---

# 10. 数据类型

系统需要支持常见的数据类型。

V1 建议支持：

```text
STRING
INTEGER
LONG
DECIMAL
BOOLEAN
JSON
```

例如：

| 配置                        | Value | Type    |
| ------------------------- | ----- | ------- |
| order.auto.cancel.minutes | 30    | INTEGER |
| order.allow.over.sell     | false | BOOLEAN |
| order.max.buy.quantity    | 10    | INTEGER |
| order.default.channel     | JD    | STRING  |
| order.strategy            | {...} | JSON    |

---

# 11. 默认值

配置项支持默认值。

例如：

```text
配置名称：订单自动取消时间

默认值：30
当前值：60
```

业务读取配置时：

```text
存在配置
    ↓
使用当前值

不存在配置
    ↓
使用默认值
```

默认值用于保证配置项在没有实际配置的情况下仍然具有合理行为。

---

# 12. Component Type

为了支持管理后台动态渲染配置项，需要定义配置项的管理组件类型。

例如：

```text
INPUT
NUMBER
SWITCH
SELECT
RADIO
TEXTAREA
```

示例：

### Boolean

```text
value_type = BOOLEAN
component_type = SWITCH
```

页面：

```text
是否开启自动取消：[ ON ]
```

### Integer

```text
value_type = INTEGER
component_type = NUMBER
```

页面：

```text
自动取消时间：[ 30 ]
```

### String

```text
value_type = STRING
component_type = INPUT
```

页面：

```text
默认物流商：[ 顺丰 ]
```

---

# 13. Options

对于 SELECT、RADIO 等组件，需要支持配置选项。

例如：

```text
配置名称：默认物流商

component_type = SELECT
value_type = STRING
```

Options：

```json
[
  {
    "value": "SF",
    "label": "顺丰"
  },
  {
    "value": "JD",
    "label": "京东"
  },
  {
    "value": "YTO",
    "label": "圆通"
  }
]
```

管理后台根据 `component_type` 和 `options` 动态渲染。

# 16. 配置查询 API

业务系统应该能够非常简单地读取配置。

例如：

```java
configService.get("order.auto.cancel.minutes");
```

提供类型化 API：

```java
configService.getString(key);

configService.getInt(key);

configService.getLong(key);

configService.getBoolean(key);

configService.getDecimal(key);

configService.getJson(key);
```

同时支持默认值：

```java
configService.getInt(
    "order.auto.cancel.minutes",
    30
);
```

---

# 17. 批量获取

为了减少业务系统访问次数，需要支持批量查询。

例如：

```text
GET /configs?group=order
```

返回：

```json
{
  "order.auto.cancel.enabled": true,
  "order.auto.cancel.minutes": 30,
  "order.allow.over.sell": false,
  "order.max.buy.quantity": 10
}
```

同时支持：

```text
GET /configs?keys=xxx,xxx,xxx
```

# 18. 配置生命周期

配置项生命周期：

```text
创建
  ↓
启用
  ↓
修改
  ↓
使用
  ↓
禁用
  ↓
删除
```

V1 可以采用软删除。

删除配置后不直接物理删除数据，而是通过状态标记：

```text
ACTIVE
DISABLED
DELETED
```

具体状态模型可以在数据库设计阶段进一步确定。

# 19. 数据库模型

推荐使用三张核心表：

```text
config_page
      │
      │ 1:N
      ▼
config_group
      │
      │ 1:N
      ▼
config_item
```

关系：

```text
ConfigPage
    │
    └── ConfigGroup
            │
            └── ConfigItem
```

# 20. 数据完整性

需要保证：

### Page

```text
code 唯一
```

### Group

```text
page_id + code 唯一
```

### Item

至少保证：

```text
key 唯一
```

如果未来需要支持多租户或不同作用域，则可以扩展为：

```text
tenant_id + key
```

当前 V1 不需要引入。

# 21. 管理后台

管理后台采用：

```text
Page
  ↓
Group
  ↓
Item
```

进行配置展示。

示例：

```text
订单配置

基础设置
────────────────────
订单超时时间       [30]
是否允许超卖       [关闭]


自动取消
────────────────────
自动取消开关       [开启]
自动取消时间       [30]


物流设置
────────────────────
默认物流商         [顺丰 ▼]
```

管理员可以直接修改配置。

# 22. 权限

V1 可以暂时只实现基础管理权限。

后续可以扩展：

```text
Page 权限
Group 权限
Item 权限
```

例如：

```text
订单配置
    ↓
订单管理员可修改

库存配置
    ↓
库存管理员可修改
```

权限体系不作为 V1 核心实现内容。

# 23. 非功能需求

## 23.1 易用性

业务方使用配置时，应尽量避免感知底层数据库结构。

理想调用：

```java
configService.getInt("order.timeout");
```

而不是：

```java
database.query(...)
```

---

## 23.2 可扩展性

数据模型应该能够支持未来增加：

* 多租户
* 配置作用域
* 配置版本
* 配置历史
* 配置审计
* 权限
* 配置导入导出
* 配置模板
* 配置缓存
* 配置变更通知

但 V1 不强制实现。

---

## 23.3 性能

由于业务配置通常属于：

> 读多写少

系统应该针对读取场景进行优化。

未来可以增加：

```text
Application
    ↓
Local Cache
    ↓
Config Service
    ↓
MySQL
```

V1 可以先直接读取数据库，不强制引入 Redis。

# 27. 核心设计原则

### 原则一：配置管理与业务数据解耦

配置中心只负责管理通用配置，不承担业务数据存储职责。

---

### 原则二：Page / Group 用于组织，Key 用于访问

```text
Page
 ↓
Group
 ↓
Item
```

主要用于：

> 管理和展示。

而：

```text
config_key
```

用于：

> 业务访问。

两者职责分离。

---

### 原则三：配置类型明确

不能把所有配置简单理解成字符串。

系统需要知道：

```text
STRING
INTEGER
LONG
DECIMAL
BOOLEAN
JSON
```

---

### 原则四：优先保证简单

系统的核心价值不是实现一个复杂的配置中心，而是：

> **用统一的模型解决大量零散业务配置问题。**

因此 V1 应保持简单，避免过度设计。

# 29. 一句话定义

> **业务通用配置管理系统，是一个面向业务系统的统一配置管理基础设施，通过 Page → Group → Item 的三级模型，对零散的业务配置和基础设置进行统一存储、统一管理和统一访问，减少业务系统为少量配置数据重复建表的成本。**

# 30. 后续设计顺序

建议按照以下顺序继续进行：

```text
需求规格
   ↓
领域模型
   ↓
数据库设计
   ↓
API 设计
   ↓
Java Domain Model
   ↓
Config Service
   ↓
管理后台
   ↓
SDK
   ↓
缓存
   ↓
权限 / 审计 / 版本
```

其中第一阶段重点应该先确定：

> **Page / Group / Item 的数据库结构和领域模型。**

数据库模型确定后，再进一步设计 API 和 Java 服务层。
